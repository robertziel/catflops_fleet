Reading the performance log…

Real traffic is not a controlled experiment — a difference between two configurations can be the traffic they were given.
how to read this

Each configuration below served whatever requests arrived while it ran — different prompt lengths, output lengths and concurrency, on different days — so a difference between two of them can be the traffic rather than the configuration. Totals like generated tok/s follow demand; per-request measures (time to first token, inter-token latency) say more about the configuration. A configuration with fewer than 30 recorded minutes is shown but not compared.

Configurations compared

how to read this

Which configuration does better at which load. Every configuration is one colour and fill everywhere on this page (the legend below); click a square in the configurations panel — the bottom-left corner of the window, or right here on a phone — to bring one forward in every chart (all puts the others back), and details to read its figures. Each square says what it is, and what its shade means, on hover.

Context, and what it costs

how to read this

The recorded minutes — the selected configuration’s when a square is picked above, otherwise the whole model’s — banded by how much context the pair was holding per request — KV occupancy × the pin’s tokens ÷ requests in flight, from figures already in the log. Seats is how many requests of that size the KV pin can hold at once. A lower bound: a prefix shared by two requests is held once, and a hybrid model’s linear-attention state shares the same pool. A minute whose engine reported no KV pool is in no band: its context is unknown, and the count of such minutes is printed under the table.

Every recorded minute

how to read this

One point per busy minute, in its configuration’s colour and dashes (the key below). A line only joins minutes that follow each other; a gap is time the cluster was idle or the gateway was not reading it, never a zero. A vertical rule marks a configuration change.

Batch size comparison

how to read this

How each max_num_seqs setting did on every saved run, one panel per workload. The bar is the mean of the runs at that setting and every run is its own mark on it — run-to-run spread is part of the answer: repetitions on one cluster generation agree within a few percent, two generations have differed by 5–10%. Colour is the speculative token count, shape is max_num_batched_tokens; a hollow mark’s settings were read from its label rather than off the engine. ▲/▼ beside a chart says which way is better. Open a run below to see where it sits.

Throughput spread inside each run

how to read this

Not an average: the range each run's throughput actually moved through, sampled every 2–3 s. The bar spans the bottom 10% to the top 10% of the samples with the mean and median marked, so a run whose worst decile collapses cannot hide behind its average. One chart per workload.
